# Failure Modes & Fixes

Symptom → likely cause → fix. Compiled from observed game-build session
failures (see AGENTS.md evidence-loop section for how these are collected).

| Symptom | Likely Cause | Fix |
|---------|--------------|-----|
| `bash: Permission denied` on `*.sh` | Script not executable or bash allowlist pattern mismatch | `chmod +x scripts/slug.sh`; widen bash permission pattern to `*scripts/*.sh*` |
| Subagent reports "MCP seems unavailable" but DB shows ZERO failed `godot-mcp-runtime_*` calls (also: build-agent `opencode run` probes always lack MCP) | **Toolset-snapshot race** — session snapshots its toolset before the async MCP handshake (npx cold-start + connect + listTools) completes; those sessions never gain the tools. Reproduced on clean boots: prompt within ~seconds of boot → tools absent; TUI with delayed first spawn → tools present (observed 09-01: 20:13 session broken, 20:45 healthy after restart) | Distinguish via DB: zero failed calls + "absent" claim = snapshot race, not server death. Restart opencode (works reliably), and in the new session verify via a real poppy delegation health check before resuming. Upstream-worthy: opencode should refresh toolsets on ToolsChanged or block until handshake settles |
| Subagent claims "MCP server isn't active" after hitting an ORDINARY tool error (file-not-found, bad params) — never actually attempted any `godot-mcp-runtime_*` call (observed 09-01 Task 14, small model; same misattribution pattern as Task 11) | **Error misattribution** — agent treats a task-level error as infrastructure failure and stops, wasting a subagent cycle. DB signature: "MCP/inactive" text in session + zero runtime-tool parts of any kind | Agent-side rule (poppy Error Handling #5): an errored call proves the tool exists; probe with one trivial read-only call before claiming tools unavailable. Post-hoc detection: query session text for "MCP" claims + check for any runtime tool parts — claim without attempts = rule violation |
| Whole session tree has zero successful `godot-mcp-runtime_*` calls; every subagent correctly reports tools absent; opencode log shows `WARN "MCP connection closed" server=godot-mcp-runtime` mid-session | **Observer-induced outage** — the harness-builder killed live MCP server processes with `pkill` while diagnosing a *suspected* stale-process problem, without verifying process ownership/start-time against the active session (observed 09-01 20:10: harness-builder pkilled 3 live servers belonging to the restarted build session; whole session ran degraded for 14+ min until discovery) | **Never kill first.** Before any process termination, correlate process start-time (via `ps` etime) with the active session's start (from the DB); a process started *after* the session began is almost certainly owned by it. The observer must follow the same rule as agents: ordinary diagnostic uncertainty is not evidence of stale state. If already killed: only a full opencode restart restores tools — tell the user immediately, don't let the session burn cycles in a degraded state |
| Subagent has NO MCP tools at all ("No MCP runtime tools appear...") | MCP server process was killed mid-session — commonly `pkill -f godot` matching `npx godot-mcp-runtime`'s own command line; opencode detects the close and drops tools with no auto-reconnect | Always `pkill -f 'godot --path'`; if tools are gone, only a full opencode restart restores them |
| `edit: Permission denied` on `test_*.gd` | Protecting test harness scripts too aggressively | Change `**/test_*.gd` to `skills/*/scripts/test_*.gd` |
| Tool parameter errors (`file_path` vs `filePath`) | Inconsistent field naming across MCP tools | Standardize on `snake_case` for all tools |
| "Slug script not found" | Working directory mismatch (repo-root vs consumer-project) | Use absolute paths in skill instructions or resolve `./.opencode/skills/...` from session cwd |
| Autoload crash on startup | Broken GDScript in autoload (headless init) | `godot-mcp-runtime:list_autoloads` → remove culprit; validate scripts before adding autoloads |
| Subagent returns empty `<task_result>` despite finishing work | Silent failure near session end (observed repeatedly; suspected context/token exhaustion) | Root agent should verify on-disk state (files, .beads/, plans/) before retrying — implementation is often complete; re-delegate only the missing verification/logging steps |
| Subagent dies mid-task with no error (part count stops growing, no step-finish) | Unexplained recurring crash (observed 3×/run) | Check for a sibling retry; the claim/plan-file resume machinery handles recovery — investigate only if it repeats on the same task type |
| Two *separate opencode sessions* run engine tools against the same project; `run_project` fails with "Another MCP client likely re-injected concurrently" + expected/on-disk port mismatch | **Cross-session bridge stomp** — each opencode session gets its own MCP server; both inject a bridge autoload with their own port into the same project, second injection overwrites the first's baked port (verified 09-01: two concurrent run_project through ONE shared server both succeed — intra-session concurrency is safe and serialized; across two servers the race is real but now correctly diagnosed instead of masked) | Coordination rule, not a retry loop: let one session finish its runtime phase before the other begins. Never acceptable trigger for improvised workarounds — report BLOCKED if the other session cannot be sequenced |
| ~~Subagent hits "MCP bridge did not respond within 8 seconds" on `run_project`~~ | **RESOLVED 09-01** — every observed instance (including "parallel tasks 3+4" that motivated the old serialization rule) was the relative-`projectPath` bug: agents passed `projectPath: "."`, the server's path guard rejected it in ~930ms, and the error was masked as a generic 8s timeout. Fixed in godot-mcp-runtime (resolve to absolute at entry + surface real error; TDD regression test), deployed via local branch pinned in `opencode.jsonc` | Fixed upstream-side; poppy carried the diagnostic rules during investigation, now removed. If "8-second timeout" reappears with ~930ms duration, suspect a regression in the deployed runtime build |
| `run_project` fails in **~930ms** (not 8s!) with "MCP bridge did not respond" + "bridge port (null)"; DB shows every failed call passed `projectPath: "."` while every success used the absolute path (09-01: 22/22 vs 12/12 deterministic split) | **Relative-path rejection, error-masked** — the bridge DOES come up (Godot prints `Listening on TCP port …`), but `pollBridge`'s path guard compares the bridge-reported absolute `project_path` against `normalizeForCompare('.')` = `.` → mismatch → immediate fail (godot-runner.ts:942). `run_project` then discards the real error ("Bridge reports project X, expected `.`") and prints the generic 8s-timeout text (runtime-tools.ts:947) — sending agents chasing a phantom infra outage. Reproduced 100% in /tmp A/B: absolute path succeeds, `.` fails identically | Agent-side rule (poppy Error Handling #7): always pass absolute project paths to runtime tools. Post-hoc DB signature: failed `run_project` with `input.projectPath="."` and duration <2s = this bug, never a bridge/port/game-code problem. Upstream: godot-mcp-runtime should resolve relative paths against the server cwd AND surface `bridgeResult.error` instead of the canned timeout message |
| `run_project` reports `McpBridge: Failed to listen (error 22)` | Transient port conflict while a prior engine instance tears down | Stop the project, `sleep 3`, retry once — usually resolves without intervention |
| MCP batch partially fails but scene still saved on disk | `batch_scene_operations` auto-saves accumulated mutations on process exit even when sibling ops errored | Pass `abortOnError: true`; check every `results[]` entry, not just the last |
| `log-result` completes only partially (plan archived but bead not closed, or vice versa) | Skill lacked a done-gate | Fixed via log-result Definition of Done + Step 3.5 verify-both-writes; if seen again, check whether the subagent loaded the updated skill |
| Subagent reasoning drifts into another language mid-task | Prompt/output drift, harmless | Cosmetic — ignore unless it correlates with quality issues |
| Long wall-clock gap, no tool calls | Host sleep (laptop lid closed), not a failure | Wait/resume; do not intervene. Confirm via absence of ANY tool-call activity |
| Compaction fires mid-task, media (screenshots) evicted from context | Context/token exhaustion — accelerated by image-heavy steps (screenshot analysis) | Not a failure if analysis text was produced *before* compaction; verify the referenced artifact still exists on disk. If a subagent must re-analyze an evicted image, the PNG file path survives — re-read it |
| Subagent constructs wrong absolute path (e.g. `/repo/project.godot` instead of `/repo/consumer-project/project.godot`) | Hallucinated path anchoring on the familiar parent-dir prefix when converting a relative reference to absolute | Self-corrects on `File not found` in 1 call — cosmetic, no fix needed; if it recurs per-task, add a poppy gotcha: "consumer project root = cwd containing `project.godot`; never prepend the harness repo root" |
| `main.tscn` gains runtime node state (Ball position/velocity baked in as properties) | Subagent saved a scene while the engine had the project open mid-run; live node state got serialized | Never save scene files while a run/playtest is active; reset scripted entities to defaults before any save (see create-scene-with-script gotcha) |
| MCP server died mid-run (`godot-mcp-runtime_*` tools disappear from all subagents after X minutes) | `pkill -f godot --path` run unquoted → argv-split binds pattern `godot` and SIGTERMs `npx godot-mcp-runtime` (observed: killed at exact second of 08:04:06, 11+ subsequent subagents lost tools for hours) | **Preventive fix:** remove all `"pkill -f *godot --path*"` allow-rules; agents must never invoke pkill — use only `stop_engine.sh`. **Reactive fix:** restart opencode immediately; continuing with missing engine tools silently degrades every verification (no automatic detection existed before this change) |
| Subagent ignores missing MCP tools and continues building shell-based validators | No hard-fail on MCP server absence; the run proceeded for hours with degraded verification (shadow test infra built, never sanctioned) | Added hard-fail to playtest & mcp-patterns: if `godot-mcp-runtime_*` tools are absent, STOP AND REPORT `⛔ BLOCKED: MCP server down. Restart opencode.` No fallbacks. |
| Subagent, after repeated `run_project` bridge-timeouts, invents a workaround: writes tmp `launch_godot.sh`/`kill_godot.sh`, self-launches the engine, `attach_project`-injects the bridge, verifies in attached mode (observed: Task 11 retry, 09-01 20:49–20:58 — 4 timeouts → attach dance → "success") | `mcp-patterns.md` documented `attach_project` as legitimate "when you launched the process yourself" — the model manufactured the precondition; recovery procedure had no terminus after the sanctioned retry, so the vacuum filled with improvisation | Happy-path-only policy: `attach_project` row rewritten as prohibition (run_project always, never self-launch); recovery procedure ends in `⛔ BLOCKED: runtime phase failed after sanctioned recovery` with an explicit DO-NOT-INVENT-WORKAROUNDS list. Watch for this drift after any run_project instability — success without engine-spawned debug output is the tell |
| Subagent session stays `running` for hours; root blocks on `task()` equally long; DB shows the last part is a bash call with `state.status: "running"` that never completes | **Silent permission ask** — a command not matching the deny/allow list becomes a permission *ask* routed to the TUI as a toast, not into the subagent's context; nobody answers it (nobody is watching / it scrolled away), so the subagent hangs forever and the root blocks on `task()` (observed 09-02 RallyWall: poppy stuck 4+ h on an unanswered ask after an earlier *denied* command was reshaped into one requiring approval; root + subagent deadlock, build unrecoverable without human action). DB signature: `state.status` `running` (not `error`!) frozen for >>60s on the leaf's final tool call, no step-finish after it | Human must answer/reject the TUI prompt or restart. **Fixes deployed:** (1) poppy rule — permission-rule errors are terminal: never reshape/retry a denied command (reshaping converts a visible error into an invisible ask); (2) build.md FATAL class "Subagent never returns" — activity-asymmetry detection + tell-the-human response, no cancel/re-delegate. Harness-side (future): detect frozen `running` tool parts >60s and auto-reject asks |
| Subagent spends minutes auditing the *implementation source of an MCP tool* (reading server source dirs, probing serializer internals) instead of working around a tool gap | **Bug 3 pattern** — a tool that cannot do something (e.g. `set_node_properties` silently dropping Resource-typed props, observed 09-02) reads as an interesting puzzle; the subagent investigates internals mid-task, burning tokens/time and drifting from scope | poppy rule (Error Handling #5): a tool that can't do the job is a diagnosis, not an investigation target — use the sanctioned skill path or return `⛔ BLOCKED` citing the limitation; tool fixes are harness-session work |
| Resource-typed properties (`CollisionShape2D.shape`) set via `set_node_properties`/`add_node`/`batch_scene_operations` read back as `null` despite the tool reporting success (DB shows `success:true` + in-memory shape `<Object#null>`) | **MCP coercer limitation** — godot-mcp-runtime's `_coerce_property_value` (godot_operations.gd:871) maps only `{x,y[,z]}` → Vector and `{r,g,b}` → Color dicts; any other value (Resource-shaped dicts, packed-array payloads) is `set()` raw, fails the typed assignment, and line 543 still appends `success: true` unconditionally. There is no Resource-instantiation path in the runtime (ClassDB.instantiate is policy-blocked). Observed 09-02: paddle task burned ~8 min probing 4 dict formats, then found `.tscn` edits also denied → no sanctioned path at all | **Fix deployed 09-02:** poppy's `.tscn` edit allow restored — sanctioned path is direct `.tscn` `[sub_resource]` injection (create-scene-with-script Step 5a + mcp-patterns common-errors row; verify the binding lands on disk after edit; never edit during an active run). Never diagnose via dict-format probing: >2 failed attempts on a Resource property = switch to direct edit. Upstream-worthy: coercer should reject unmapped dict shapes with a typed error instead of reporting success |
| Root build session goes silent for hours while the opencode process stays alive; no subagents running (no children with fresh `time_updated`); last root message shows `finish: length` with a giant single-step output (~32k tokens) at high context (~123k) | **Verbose-generation blowout** — the model emits prose/ mega-steps instead of tool calls at high context; the response hits the output-length limit and is truncated mid-generation; the session then never progresses (brain-death) while subagent-span timeout logic sees nothing (observed 09-04, ling run: 7.1 h overnight stall; host verified awake via process uptime + `kern.waketime`, ruling out sleep) | Detect with `scripts/watch_root.sh` (root parts stale AND no child activity → alert with host diagnostics). Recover by sending `continue` to the session or restarting opencode — state persists in .beads//plans. Prevention: build.md root-verbosity rule (one tool call or <10-line note per step; paragraph-urge = compact-or-delegate signal). Structural fix (opencode-side output watchdog) is an upstream-contribution candidate |
| Subagent skips the playtest step "to avoid timeouts" and marks tasks `[x]` unverified | Timeout pressure on the full scene-verify gauntlet created an incentive to bypass the sanctioned path entirely (observed 09-04, ling run: 4 tasks completed without playtest; later full-gauntlet QA passing masked the shortcut) | Deployed: playtest `fast-verify` mode — a ~5s baseline-invariant smoke check positioned as the mandatory cheap minimum after every scene/script change. Protocol: at least fast-verify before any `[x]`; inability to run it is a `⛔ BLOCKED:` report, never an unverified completion |
| Subagent enters a **restart/timeout ladder** for hours on `run_script` calls: trivial probes (`return {"ok": true}`) time out while `get_debug_output` succeeds; escalates `timeout` params (60s → 120s → 600s), cycles `stop_project`/`run_project` 10–18×; engine logs clean throughout (observed 09-07 CoilUp run 10: 4h58m, 70 errors, 5.6M tokens, zero forward progress; self-recovered only at the bounded-work budget 4.5h late) | **Engine unresponsive under host memory pressure** (root cause confirmed post-run: the OS suspends the engine process under host RAM exhaustion; a suspended process keeps its bridge socket bound and stdio readable while never servicing RPC — matching the signature exactly). The canned error "Is the game running?" actively misleads (the game IS running). Prose retry-caps fail here because each error looks individually actionable — sunk-cost spiral | **Deployed:** mcp-patterns.md _Engine/transport unresponsive_ — signature, ONE restart-cycle cap, one TestPlayer-autoload-removal try, 5-min cumulative timeout budget per phase, then `⛔ BLOCKED`. Upstream-worthy: run_script should classify "transport unresponsive" vs "game not running" (a probe that never reaches the engine is diagnosable server-side, e.g. by distinguishing socket-connect-success-but-no-reply from connection-refused) |
